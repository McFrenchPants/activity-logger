# Design spec — Room schema v1 + migration test infrastructure (backlog item 3)

Status: **approved by owner** (2026-09-16).
Branch: `feature/room-schema`, off `main` at 2640ca2.
Source: `docs/IMPLEMENTATION_HANDOFF.md` "Step 2 — Persistence",
`docs/DATA_MODEL.md`, `docs/DOMAIN_MODEL.md`, `docs/ARCHITECTURE.md` §10-12,
`docs/REQUIREMENTS.md` CAP-003/004, COR-001..005, DB-001..005, REL-001..003,
`docs/TEST_STRATEGY.md` §8, §11, ADR-007/008/009/012/014/018.

Audience: agents. The owner-facing summary is given in chat, not here.

## 1. Goal

Replace the scaffold's placeholder Room database in `core-data` with the real
phone-authoritative schema, version 1, so that Steps 3 (domain services) and 4
(AI vertical slice) have somewhere correct to write. The schema must make the
project's integrity rules hard to break by accident, and the project must be
able to prove, by automated test on the development machine, that future
schema versions keep every row of user history.

## 2. Non-goals

- Domain services (activity repository interface, temporal resolver, candidate
  selector, interpretation validator, correction service) — Step 3.
- Any AI, speech, UI, or Wear transport code.
- The watch-side `watch_capture_outbox` — watch-local, owned by Step 8.
- Seed/curated canonical activities or aliases — belongs with the semantic
  corpus (Step 5) / first-run behaviour, not the schema.
- Activity merge behaviour, transcription corrections, hard deletion, export,
  backup/restore, sync fields (version, device origin, tombstone). Schema must
  not make these impossible (DATA_MODEL §6, §8-10); it does not implement them.
- On-device instrumented test runs. Routine gate is host-side only (see R9).

## 3. Requirements

**R1 — Six tables, as `DATA_MODEL.md` §2 defines them:** `raw_captures`,
`canonical_activities`, `activity_aliases`, `interpretations`,
`activity_occurrences`, `corrections`. Column names, nullability and listed
indexes follow `DATA_MODEL.md` unless §5 below records a deliberate difference.

**R2 — Globally unique text identifiers** for every row (ADR-014, DB-004),
generated by the app, never by SQLite autoincrement.

**R3 — Referential integrity enforced by SQLite**, not only by convention:
every `*_id` column that references another table is a real foreign key.
No foreign key cascades deletes into raw captures, interpretations or
corrections — deleting a referenced row must fail, not silently erase evidence.

**R4 — Raw text is write-once.** The data layer offers no operation that can
change `raw_captures.raw_text`, `source`, or `captured_at` after insert. The
only mutable raw-capture fields are `processing_state` and `updated_at`
(DATA_MODEL §5, ADR-007). A test proves a raw capture's text is byte-identical
after every write operation the layer exposes has been exercised against it.

**R5 — Interpretations are append-only.** No update or delete of an
interpretation row is exposed. Re-interpretation inserts a new row.

**R6 — Corrections are append-only and are the only way an occurrence's
activity, time, precision or state changes after creation** (ADR-008,
COR-002..004). Applying a correction writes the correction row and updates the
occurrence in one transaction, recording the previous and new values.

**R7 — Accepting an interpretation is one transaction** (ARCHITECTURE §12,
REL-003): insert the validated interpretation, create the canonical activity
if the interpretation proposes a new one, create the occurrence pointing at
that interpretation, and advance the raw capture's processing state. Either all
of it is stored or none of it is. Retrying the same acceptance for the same raw
capture must not create a second occurrence.

**R8 — Processing state and enumerations** are stored as stable text names
(not ordinals), using the vocabularies in DOMAIN_MODEL §8-10 and
DATA_MODEL §2/§7. Reordering or adding a Kotlin enum constant must not change
what an existing row means.

**R9 — Tests run on the development machine without a phone attached**, as
part of `./gradlew test` (or an equally routine command recorded in the plan).
They cover at least: TEST_STRATEGY §8's correction scenario end to end, R4, R5,
R7 including the retry case, foreign-key refusal of evidence-destroying deletes,
and the indexed "latest occurrence of activity X" query that "When did I last
mow?" will rely on.

**R10 — Migration test infrastructure exists and is exercised now**, even
though only version 1 exists:
- the exported schema JSON for version 1 is committed and is the baseline;
- a reusable test harness can create a database at an older exported version,
  fill it with representative data covering all six tables, run migrations to
  the current version, and assert raw captures, canonical activities,
  interpretations, corrections and occurrence relationships all survive
  (TEST_STRATEGY §11);
- the harness is proven against version 1 (create → populate → open at current
  version → validate against the export), so the first real migration only has
  to add a test case, not build infrastructure;
- a test fails the build if the production database builder is ever configured
  with any destructive-migration fallback (DB-003).

**R11 — Scaffold placeholders are removed**: the placeholder entity, DAO,
database and its exported schema JSON in `core-data`, and the placeholder in
`core-domain` if the domain vocabulary lands there.

**R12 — Documentation matches the result**: `DATA_MODEL.md` updated for every
difference recorded in §5; an ADR for the identifier choice (§5.1), which
closes the "UUID vs UUIDv7" open decision in `PROJECT_STATUS.md`.

## 4. Constraints

- Room 2.8.5 via KSP 2.3.12, Kotlin 2.3.x only (ADR-022). Any new library
  (test libraries, SQLite driver) must be verified to resolve against the
  current toolchain before entering the version catalog, and pinned there.
- No ML Kit anything in `core-data` or `core-domain` (ADR-023).
- `core-domain` stays a pure Kotlin/JVM module with no Android or Room types.
- `exportSchema = true`; schema JSON stays in the tracked `core-data/schemas`
  directory.
- No logging of row contents from the data layer (AGENTS.md §11, PRI-003).
- Phone backup is already disabled (`allowBackup="false"`); this work must not
  change that.

## 5. Decisions taken for this spec (orchestrator, technical)

These are implementation-level calls within the existing design; none changes
product behaviour. Each is recorded here so the plan and reviewers can hold the
implementation to it.

### 5.1 Identifiers: UUIDv7 as canonical lowercase text

UUIDv7 (ARCHITECTURE §11's first preference) because its time ordering keeps
the primary-key B-trees append-mostly and makes IDs roughly sortable by
creation. Source: Kotlin standard library `kotlin.uuid.Uuid` if its V7
generator is available and usable at the pinned Kotlin 2.3.21 (it is
`@ExperimentalUuidApi`; opting in is acceptable and must be confined to one ID
factory). **If the plan's first task cannot confirm that API exists at 2.3.21,
fall back to random UUIDv4 via `java.util.UUID`** — do not add a third-party
UUID library for this. Either way, generation sits behind one small interface
so tests can supply deterministic IDs. Recorded as a new ADR.

### 5.2 One occurrence per raw capture in schema v1

`activity_occurrences.raw_capture_id` gets a **unique** index (DATA_MODEL lists
a plain index). DATA_MODEL §3 already shows the relationship as 1:1, and a
unique constraint is the cheapest guarantee that a retried acceptance (R7) or a
duplicate watch delivery cannot double-log an activity. If a future design
allows one utterance to log several activities, that is a normal migration.
`DATA_MODEL.md` updated.

### 5.3 Capture time zone is stored

Add `raw_captures.captured_zone_id TEXT NOT NULL` (IANA zone ID at capture
time). ADR-018 forbids fabricating precision: a `DATE_ONLY` occurrence stored
as an instant is only meaningful together with the zone the date was resolved
in; without it, "yesterday" logged before travelling can display on the wrong
day afterwards. Occurrences and corrections are resolved in that zone, so no
further zone columns are added. `DATA_MODEL.md` updated.

### 5.4 Canonical activity names are not unique in the database

`canonical_activities.normalized_name` keeps a plain (non-unique) index as
DATA_MODEL specifies. Merged/archived activities may legitimately share a name
with an active one, and Room cannot declare a partial unique index. Preventing
duplicate *active* activities is activity-resolution policy (Step 3), not a
schema constraint. `activity_aliases` does get a unique index on
`(canonical_activity_id, normalized_alias)` per DATA_MODEL.

### 5.5 Corrections do not fabricate interpretation rows

A user correction writes a `corrections` row and updates the occurrence; it
does not invent a synthetic "user interpretation" (DATA_MODEL §12 makes this
optional). `effective_interpretation_id` changes only when a real new
interpretation is accepted, and that change is itself recorded in a correction
row via its previous/new interpretation columns. `source` on the correction
carries the user-originated flag COR-004 asks for.

### 5.6 No SQLite triggers

Raw-text immutability is enforced by the data layer's API shape plus tests
(R4), which DATA_MODEL §5 allows. Triggers are not tracked by Room's exported
schema, so every future migration would have to remember to recreate them —
a silent-loss risk worse than the one they guard against.

### 5.7 Where the code lives

Room entities, DAOs, the database class, type converters and the ID factory
live in `core-data`, internal where possible. The stable vocabularies (activity
state, resolution, processing state, time precision, visibility, correction and
alias sources) live in `core-domain` as plain Kotlin enums, since Step 3's
services and Step 4's validator need them without depending on Room. Public
repository interfaces are **not** designed here — that is Step 3 — so
`core-data`'s DAO-level operations are the integrity boundary for now.

## 6. Open questions

None requiring the owner. Two items for the plan's first task to settle by
verification, not guesswork:

- Whether Kotlin 2.3.21's standard library exposes a UUIDv7 generator (§5.1).
- The host-side test approach for Room in an Android library module (e.g.
  Robolectric, or Room's bundled SQLite driver) and the exact version that
  resolves on this toolchain — chosen by what actually runs, including
  `MigrationTestHelper`, and recorded with its pinned version.
